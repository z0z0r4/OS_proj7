## 3. 三个非法方向探针

服务端在收到布防后的第一个 `FS_READ` 时执行：

| 探针 | 调用 | 新代码期望 |
|---|---|---|
| `n=0` | `svc_xfer(SVC_FS, 99, gaddr, badmark, 0)` | -1（旧代码循环不执行，返回 0） |
| `n=4` | `svc_xfer(SVC_FS, 99, gaddr, badmark, 4)` | -1（旧代码走 TO_CLIENT，写入 `BAD!`） |
| 64 位 | RISC-V fault-only `svc_xfer_wide(SVC_FS, 0x100000000ULL, ...)` 内联 `ecall` | -1（`argint` 会截断为 0 而接受） |

结果编码：`accepted` 的第 0/1/2 位分别表示三个探针“未被拒绝”；全部拒绝时返回 -1，否则返回 `-1-accepted`。客户端断言 `xn == -1`，因此任一探针被接受都会失败。缓冲区初始化为 `Z`，若 `n=4` 或 64 位探针被错误接受则出现 `BAD!`，`memcmp(xb,"ZZZZ",4)` 同时失败。

64 位探针仅 RISC-V 编译；其他架构作为静态审查项，文档区分“代码验证”与“运行时验证”。

## 9. 最终收尾小修订

人工复核后只收紧测试钩子，内核逻辑不变：

1. `src/fssrv/main.c` 的魔法 mount 匹配由前缀匹配改为精确匹配：
   `strlen(r->s1) == 11 && strncmp(r->s1, "__xferdir__", 11) == 0`。
   带后缀的 `__xferdir__<suffix>` 不再布防。消息由 `sysfile.c:pathcall` 的 `memset` + `safestrcpy` 产生并 NUL 结尾，`dispatch` 还把 `s1[MAXPATH-1]` 置 0，因此 `strlen` 读取安全。
2. 核对 `svc_xfer_wide()`：fault 构建反汇编（`u3-final-fault-20261107-145712/fssrv.asm`）确认参数映射为
   `a0=SVC_FS(1)`、`a1=0x100000000`、`a2=gaddr`、`a3=&badmark`、`a4=4`、`a7=SYS_svc_xfer(27)`，随后 `ecall`，返回值在 `a0`。
   内核按 arg0..arg4 读取，映射一致；函数被内联，符号表中无独立条目，但反汇编可见完整序列。
3. 复跑结果：
   - `make fault` + `make run`：**69 OK / 0 FAIL，Result PASS**，新断言 `invalid xfer directions rejected without copying` 为 OK（`u3-final-fault-20261107-145712/`）。
   - 普通 `make ext2`：exit 0；`P0_TEST_HOOKS` 计数 0，普通 `_fssrv`/`_fsfault` 中 `__xferdir__` 计数 0，kernel 中 `svc_hold` 计数 0（`u3-final-normal-20261107-145712/`）。
