## 修订 1：权限检查拆成显式条件

```c
if(p != initproc)
  return -1;
if(id != SVC_FS)
  return -1;
if(svc[SVC_FS].server != 0)
  return -1;
```

- 任何 `svc[]` 访问都发生在服务 ID 验证之后（`svc[SVC_FS]` 为常量下标）。
- 原短路表达式 `p != initproc || id != SVC_FS || svc[id].server != 0` 的语义保持不变：非 init 一律 -1；init 且 ID 非法一律 -1；init 且服务存活一律 -1。
- 无 ABI / IPC / 返回值变化。

## 修订 2：删除无判别力的断言

删除 `fsfault.c` 中：
`check(svc_restart(0) < 0 && svc_restart(2) < 0, "invalid service ids rejected");`
并同步删除 `tests/fault/run.sh` 对应 `--expect`。

原因：这两个调用来自普通用户进程，返回 -1 的原因是 init-only 权限拒绝，并不能独立证明服务 ID 校验；保留会误导测试覆盖范围。

## 修订 3：fault → 普通构建的切换路径核查

实际构建路径（顶层 `Makefile`）：

| 目标 | 构建命令 | 是否先 clean |
|---|---|---|
| `test_baseline` / `public_vfs` / `ext2` / `fat32` / `error` / `semantics` / `persist` / `smp` | `cd src && make ARCH=... clean && make ... kernel/kernel [&& rm -f *.img] && make ... fs.img` | 是 |
| `fault` | 同上，另在两处 make 传 `KEXTRA=-DP0_TEST_HOOKS` | 是 |
| `mount_lifecycle` / `remount_io` / `mount_storm`（`prepare_extended_case`） | 同上，先 `make clean` | 是 |
| `loongarch_*` | 转调对应目标（同样 clean） | 是 |
| `make run` | `tests/<case>/run.sh` → `run_qemu_case.py` → `cd src && make ARCH=... CPUS=... qemu` | **否** |
| `tests/run_all.sh` | 逐个 `make <case>` + `make run` | 每次 prepare 均 clean |
| `tests/full_usertests.sh` | 自身先 `make ARCH=... clean` | 是 |

结论：
- **受支持的“从 fault 切换回普通构建”路径安全**：每个普通 prepare 目标都无条件执行 `make clean`，不会复用带 `P0_TEST_HOOKS` 的 `.o`；本次实测在 fault 构建后直接执行 `make ext2`，其 `build.log` 首行即 clean 命令，随后构建日志中 `P0_TEST_HOOKS` 计数为 0，kernel 无 `svc_hold` 符号，`_fsfault` 无测试字符串。
- **唯一非 clean 路径**是 `make run` 内 runner 的增量 `make qemu`。正常流程中 prepare 刚完成构建，全部目标为最新，make 不编译；若在 prepare 与 run 之间修改源码或时间戳异常，make 会以**不带 KEXTRA** 的方式重编变化文件，从而与该次 fault 构建的其余目标文件混用。此路径不会静默通过：fault 测试的钩子断言会缺失并失败。
- 加固已实施（用户批准）：`tests/fault/run.sh:28` 在调用 runner 前 `export KEXTRA=-DP0_TEST_HOOKS`。已核实 `run_qemu_case.py:69-76` 的 `subprocess.Popen` 未传 `env=`（子进程继承父环境），make 再将环境变量传给编译子进程。该改动仅影响 fault 用例，不重构构建系统；`grep -rn KEXTRA tests --include='*.sh'` 仅命中 `tests/fault/run.sh`。
